# AGENTS.md

## Scope

This document defines the permanent rules and authorization limits for
AI-assisted development in `nmrglue-ng`.

Procedural details live in the project's OpenCode skills, in
`CONTRIBUTING.md`, and in `maintainer/`. Load the relevant skill before
starting work.

**Read `CONTRIBUTING.md` at the start of each session.**

When rules overlap, follow the stricter requirement.

---

## Core Principles

`nmrglue-ng` is an independent continuation of `nmrglue`. Preserve this
identity:

```text
distribution: nmrglue-ng
import:       nmrglue
```

Backward compatibility with the historical `nmrglue` API is a priority. Broad
refactors and general style rewrites are not project goals.

Priorities:

1. scientific correctness;
2. behavior preservation;
3. minimalism;
4. reviewability.

Prefer small, reversible, reviewable changes.

---

## Starting From a Known Baseline

* Branch from an updated `master` and announce the baseline explicitly
  (branch, commit, `git status`) before the first edit.
* Preserve local modifications. Never overwrite, stash, or discard work that
  is not part of the task.
* Read the applicable instructions, skills, and maintainer documents before
  acting.

---

## Scientific Correctness

Treat changes involving any of the following as scientifically sensitive:

- frequencies, spectral widths, or axes;
- point, Hz, or ppm conversion;
- carrier, reference, or observation frequency;
- quadrature, complex data, or endianness;
- dimensions or axis ordering;
- instrumental metadata;
- reading or writing a data format.

Every scientifically sensitive change must include a regression test and a
justification based on an appropriate source, such as a format specification,
verified vendor-software behavior, a checked real file, a scientific
publication, or relevant NMRPipe, TopSpin, or equivalent behavior.

**Never change an expected test value merely to make a test pass.** First
explain why the new value is scientifically correct.

## Defect Workflow

1. Reproduce the defect before fixing it, and record how it was reproduced.
2. Search for a fix that is minimal and generic rather than one tailored to a
   single symptom or dataset.
3. For a writer change, add a suitable round-trip test when reasonably
   possible (`read -> write -> read`).
4. Validate with the smallest test scope that proves the claim.

Synthetic fixtures are valuable, but they do not always replace validation
against a real file when vendor conventions or metadata are involved.

## Test Data: Three Distinct Categories

Never blur these categories, and never let one silently stand in for another:

| Category | Meaning |
|---|---|
| **Versioned fixture** | Small, redistributable, committed to this repository. |
| **Local corpus** | External dataset downloaded separately, never committed. |
| **External reference** | Values generated by external software (e.g. NMRPipe). |

Additional rules:

* **Never modify the canonical corpus during a test run.** Tests that write
  must work on a temporary copy (for example via the pytest `tmp_path`
  fixture).
* A skipped test is not a validated test. Never present a `skipped` result as
  evidence that a behavior is correct; report the skip and its reason.
* Never version or republish data whose provenance and redistribution rights
  are not established. Document provenance, license, and checksum for every
  external dataset (see `CONTRIBUTING.md`).

Keep the test categories explicit in code and reporting:

1. **Self-contained tests** — no external data, no external software. These
   are the standard CI profile (`-m "not dataset and not external_software"`).
2. **Dataset-dependent tests** — need the external `data/` directory. A missing
   dataset is not a product failure.
3. **External-software tests** — need NMRPipe or another external program.
4. **Optional-dependency tests** — need an optional Python package.

Do not claim that the CI profile covers the complete suite.

## Change Scope

Prefer small, coherent pull requests. Keep infrastructure, packaging,
documentation, bug fixes, scientific or API changes, and performance work
separate unless combining them is demonstrably necessary.

**Never mix several independent defects in the same pull request.**

Preserve existing behavior and the public API when that does not compromise
scientific correctness. Any incompatible change must be explicitly
identified, justified, tested, documented, and accompanied by migration
guidance when needed.

Update the relevant maintainer documents (`maintainer/roadmap.md`, a dated
`maintainer/audits/` entry) when a decision or durable knowledge must survive
the task. Prefer editing an existing document over creating a new one.

## Relationship With Upstream

[`jjhelmus/nmrglue`](https://github.com/jjhelmus/nmrglue) is the historical
upstream project. **Preserve its history and attribution.** When adapting
upstream work:

- preserve authorship when possible;
- reference the original issue or pull request;
- do not present existing work as new;
- document substantial adaptation.

Development in `nmrglue-ng` is independent from upstream contribution. A fix
that is small, generic, reproducible, independent of `nmrglue-ng`-specific
choices, and compatible with upstream's API and scope is a *candidate* for
upstream contribution — never an automatic one. Report the opportunity in the
work summary.

**No additional upstream contribution while PRs #279–#282 have received no
significant maintainer feedback.** See `maintainer/roadmap.md` for the current
list and for the obligation to restart any future portage from the
then-current `jjhelmus/nmrglue:master`.

Branding, packaging, governance, and roadmap choices specific to
`nmrglue-ng` are never proposed upstream. Do not withhold a generally useful
fix merely to differentiate `nmrglue-ng`.

## Authorization Limits

The maintainer controls branches, commits, pushes, pull requests, tags, and
releases.

Unless explicitly delegated:

* do not create branches;
* do not commit;
* do not push;
* do not open or merge pull requests;
* do not tag, upload, or release;
* do not open an upstream issue or pull request;
* do not install or upgrade dependencies in the user's primary environment.

**No merge, tag, upload, or release without explicit authorization.**

When a task is authorized, proceed to a validated solution without asking for
confirmation on ordinary technical choices.

---

## Review

The implementer's self-verification is **not** an independent review.

A separate review in a fresh session is required for any change affecting
scientific computation, file-format reading or writing, the public API, test
infrastructure, packaging, CI, or release process. It is also required for
any modification to an existing assertion, tolerance, scientific expected
value, fixture, marker or skip, or corpus-management behavior.

A separate review is not required for pure documentation edits or for a
test-only addition that verifies existing behavior without changing any of
those validation semantics. See the `nmrglue-ng-review` skill.

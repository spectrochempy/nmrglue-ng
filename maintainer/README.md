## Evidence and update rules

- `reports/` contains versioned, curated technical reports. Each names its
  date, code baseline, evidence source, validation performed and omitted,
  current conclusion, and remaining decisions. A report records what was
  established at that baseline, not a guarantee about all later commits.
- `audits/` remains ignored local working material: detailed session notes,
  reproducer development and draft correspondence. Preserve those originals;
  do not force-add the directory. Other contributors must not need it to
  understand a shared conclusion.
- After an audit, save the local report as required by `AGENTS.md`, review the
  roadmap, and consolidate durable findings into an appropriate shared report
  when warranted. A new report is useful for a distinct subject; do not create
  a second copy of the same evidence for every session.
- State whether results were run by the current author, transcribed from a
  prior audit, or taken from hosted CI. Keep exact counts, skip reasons, tested
  software versions and code commits. Never relabel consolidation as a fresh
  validation or an independent review.
- Corrections must identify the superseded conclusion. Keep useful scientific
  evidence, sources and attribution, but remove local paths, temporary-file
  inventories, pending commit instructions and outbound-message drafts.
- Keep external links when they support a technical conclusion or attribution.
  Routine correspondence and publication status do not belong in reports.
- Approval of a report does not approve proposed scope reductions, change
  release gates, or authorize an upstream submission.

## Agent workflow

[AGENTS.md](../AGENTS.md) defines authorization limits and review requirements.
The shared skills under `.agents/skills/` cover development, independent review
and release-readiness auditing. These reports are evidence for those workflows,
not a replacement for them. A maintainer report can accompany a PR; local
working notes stay ignored.
